# 中国象棋 AI（双引擎 · 六档难度 · 纯前端）

[English Version](README.md) | **中文文档**

一款纯前端、零后端的中国象棋对弈应用：**低难度档位用内置的 JavaScript 引擎即时应着，
高难度档位切换到编译成 WebAssembly 的 Pikafish 引擎（NNUE 神经网络评估 + 多线程搜索）。**

---

## 1. 难度分级与双引擎架构

应用提供**六档难度**。之所以要两个引擎，是因为它们的成本曲线完全不同：
低档位需要"点开即玩"，高档位需要"真正的强度"，而这两件事没法用同一个引擎同时满足。

| 档位 | 名称 | 引擎 | 搜索方式 | 首次加载 |
|:---:|:---:|---|---|---|
| 1 | 入门 | Wukong（内置 JS） | 深度 1 + 高概率随机失误 | **0 字节** |
| 2 | 初级 | Wukong（内置 JS） | 深度 2 + 中概率随机失误 | **0 字节** |
| 3 | 中级 | Wukong（内置 JS） | 深度 4 + 低概率随机失误 | **0 字节** |
| 4 | 高级 | Pikafish（WASM） | 深度 10 + MultiPV(3) softmax 采样 | 49 MB |
| 5 | 大师 | Pikafish（WASM） | 深度 12 | 已加载 |
| 6 | 宗师 | Pikafish（WASM） | 固定 5 秒思考 | 已加载 |

**档位 1~3 完全不需要下载任何权重**，打开网页就能下棋；只有选择 4~6 档时才会
首次下载一次 49MB 的神经网络权重，之后由浏览器缓存复用。

> **为什么不用引擎自带的难度选项？**
> Pikafish 源自 Stockfish，但**没有** `Skill Level` / `UCI_Elo` / `UCI_LimitStrength`
> 这三个选项（已逐文件核实 `src/engine.cpp`、`src/search.cpp`、`src/search.h`，
> 全仓库搜索 `UCI_Elo` 命中为 0）。它实际只注册了 `Threads` / `Hash` / `MultiPV` /
> `Move Overhead` / `EvalFile` 等。所以"弱"必须由应用自己造：
> 用 `MultiPV` 拿到多个候选着法，再按**厘分 softmax 温度**采样 ——
> 温度越高越容易选中次优着法，同时用损失上限保证它"弱但连贯"，
> 不会出现白送车、白送将这种"看起来像坏了"的棋。

## 2. 核心亮点

* **双引擎可插拔**：`js/engines/bridge.js` 把"Worker 型 WASM 引擎"和"同线程 JS 引擎"
  收敛成同一套异步接口（`load` / `unload` / `search` / `status`），主程序不需要知道
  底下是什么。请求-响应用自增 `seq` 配对，天然丢弃过期回包。
* **零下载档位，点开即玩**：档位 1~3 由仅 57KB 的 Wukong 引擎承担，页面加载即预热。
* **权重只下载一次**：49MB 权重走流式下载（有**真实**进度条，不是假动画），
  并写入 Cache Storage，刷新页面不重下。
* **悔棋**：人机对战时连撤两步（AI 一步 + 自己一步），撤销后同步重建侧栏记录。
* **完整规则判定**：落子提示点会排除「白脸将」与「自杀着」；
  终局由引擎报出的合法着法数判定（为 0 即被将死或困毙，象棋里无子可走即判负）。
* **不伪造数据**：侧栏的深度、节点数、NPS、耗时、评估分全部来自引擎的真实 UCI 输出；
  采样后走的如果不是引擎首选着法，会明确标注「次优」。取不到的字段一律显示 `-`。
* **主线程零卡顿**：两个引擎都运行在独立 Web Worker 中，主界面始终流畅。

## 3. 本地开发

项目内置静态开发服务器 [server.py](server.py)，默认绑定 **`6324`** 端口，
并自动补齐 WASM 所需的跨源隔离响应头（COOP / COEP）：

```bash
python3 server.py
# 然后访问 http://127.0.0.1:6324/
```

服务器对 `*.nnue` 与 `*.wasm` 发送长缓存头（文件名含内容哈希，可安全 immutable），
其余资源保持 `no-store` 以便改完刷新即见。

> ⚠️ 必须通过 HTTP 访问。直接 `file://` 打开会因为拿不到跨源隔离环境而无法启用
> Pikafish 的多线程路径（档位 1~3 不受影响）。

## 4. 架构分层

```text
+--------------------------------------------------------------+
|                     Web UI（视图层）                          |
|   js/xiangqiboard.js（棋盘与菜单） + js/app.js（对局控制）     |
+------------------------------+-------------------------------+
                               | 交互事件
                               v
+--------------------------------------------------------------+
|              js/engines/bridge.js（引擎可插拔层）             |
|     load / unload / search / status  ·  seq 配对 · 超时兜底    |
+--------------+-----------------------------+-----------------+
               |                             |
               v                             v
+----------------------------+  +------------------------------+
| js/engines/wukong/         |  | js/worker/pikafish.worker.js |
|   wukong.worker.js         |  |  （包在 Emscripten 产物外面） |
| 纯 JS 同步搜索 → 档位 1~3  |  |  权重缓存 + multipv 采样      |
+----------------------------+  +---------------+--------------+
                                                | WASM / pthread
                                                v
                                +------------------------------+
                                | pikafish-engine.wasm (C++17) |
                                |  + 49MB NNUE 神经网络权重     |
                                +------------------------------+
```

`js/difficulty.js` 是两端共用的档位表与走子采样函数，主线程与两个 Worker 都加载它，
保证"难度"只有一处定义。

## 6. 部署

推荐 **GitHub Pages**：单文件上限 100 MiB，装得下 49MB 的权重。

> ⚠️ **Cloudflare Pages 不可用**（除非另找地方放权重）：它的单文件上限是 **25 MiB**，
> 49MB 的 `pikafish-*.nnue` 会被拒绝部署。

静态托管无法自定义响应头，因此：
- COOP / COEP 由 `coi-serviceworker.js` 注入（首次访问会自动 reload 一次以激活）；
- 权重的持久缓存由 Worker 内的 Cache Storage 负责 —— GitHub Pages 对所有资源只发
  `Cache-Control: max-age=600`，只靠 HTTP 缓存的话用户隔十分钟回来就要重下 49MB。

**带宽提醒**：每次首次访问（无缓存）要传 49MB。GitHub Pages 免费版带宽软上限约
100 GB/月，折算下来约 2000 次首次访问；回访用户有缓存，成本极低。

## 7. 实测校验

难度参数不是拍脑袋定的，下面两组数据都是本机跑出来的。

### 7.1 相邻档位头对头（机机对战，红黑互换）

| 对战 | 结果 | 结论 |
|---|---|---|
| 1 入门 vs 2 初级 | **0 : 6** | 2 全胜 |
| 2 初级 vs 3 中级 | **1 : 5** | 3 明显强 |
| 3 中级 vs 4 高级 | **0 : 18** | 4 全胜 |
| 4 高级 vs 5 大师 | **0 : 5**（1 和） | 5 明显强 |
| 5 大师 vs 6 宗师 | **2 和** | 都接近完美，互交白卷 |

**没有倒挂**。第 3/4 档之间是「纯 JS 引擎 / WASM 引擎」的分界，强度落差天然最大
（实测第 4 档对第 3 档 18 局全胜）—— 这是引擎量级的差异，不是参数没调好。

### 7.2 每步损失（厘分，越小越强）

取 4 个真实中局局面，以第 5 档（depth 12）的评估为基准，
损失 = 该局面最优评估 − 所走着法走完后的评估（行棋方视角）：

| 档位 | 平均损失 | 中位数 | P90 | ≤30 厘分的比例 |
|---|---|---|---|---|
| 1 入门 | 83 | 100 | 165 | 42% |
| 2 初级 | 14 | 8 | 46 | 75% |
| 3 中级 | 22 | 27 | 61 | 63% |
| 4 高级 | 27 | 6 | 127 | 70% |
| 5 大师 | −1 | −1 | 7 | 100% |
| 6 宗师 | −7 | −8 | 7 | 100% |

2~4 档的平均值在噪声范围内（单次采样的方差很大：这一档"送不送子"取决于
随机劣化有没有触发），所以**以中位数与头对头胜负为准**，不要按平均值微调。
第 4 档的温度（120）就是照这张表定的：40~60 时几乎等于第 5 档（失去意义），
170 时又和第 3 档拉不开。

### 7.3 已实测的其他项

- **零下载**：全新浏览器 profile 首访 → 选第 1 档 → 走一子拿到应着，
  服务器日志中 `*.nnue` 请求数为 **0**。
- **只下载一次**：整轮实验（含数十次 Pikafish 搜索 + 多次刷新页面）
  `*.nnue` 请求数只增加 **1**；刷新页面后为 0。
- **跨源隔离**：`window.crossOriginIsolated === true`，`SharedArrayBuffer` 可用，
  侧栏 NPS 在百万量级（单线程只有十万量级）。
- **规则判定**：12 个真实中局局面上，「穷举 `isLegalMoveFull`」「引擎 A 报的合法着法数」
  「引擎 B 报的合法着法数」三者**逐一致**（36/36、44/44、40/40 …）——
  既没有放行非法着法，也没有误杀合法着法。
- **悔棋**：人机对战下连撤两步回到自己走子前，撤完仍可继续对弈。

### 7.4 移动端注意

`pikafish-engine.js`（Emscripten 产物，本项目刻意不改）里硬编码了
`setoption name Hash value 256`，即 **256MB 置换表**。手机上它和 49MB 权重
共用一个 WASM 堆，容易触发 OOM 被杀。包装层 `js/worker/pikafish.worker.js`
在检测到 `navigator.deviceMemory <= 4`（GB）时会把这条命令改写为 **64MB**
（拦截点见该文件 `applyMemoryCap` 的注释）；取不到 `deviceMemory` 或桌面端保持 256MB。
即便如此，**低端手机仍建议只用 1~3 档**——那是纯 JS 引擎，内存占用可以忽略。
